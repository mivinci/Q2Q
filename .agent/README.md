# AI 协作说明

本目录整理维护者在实际协作中明确表达、反复确认的偏好，供不同 AI 接续开发。它不是个人画像，也不是当前任务清单。项目架构约定见 [architecture.md](architecture.md)，具体需求和完成状态见 `todos/`。

## 沟通与推进

- 默认使用中文，技术名词、API 和代码标识保留原文。说明直接、具体，讲清改什么、为什么以及边界。
- 用户说“继续”“下一项”时，先接续最近已确认的目标和 todo，说明当前做到哪里，再推进下一项；不要自行切换产品方向。
- 多阶段需求先把方案、边界和验收项记入 `todos/`，获准后依次实施。小修复无需强行扩成设计文档。
- 对已经确认的方案和动作直接执行，不重复征求确认。真正缺少会改变结果的信息时才提出具体问题。
- 做架构判断前先读 README、相关文档和实际实现，不能只凭命名或旧对话推断。
- 汇报区分“代码已实现”“本地验证通过”“CI 通过”“PR 已合并”，不要混用。未验证和当前限制如实说明。

## 代码结构与抽象

- **目录保持扁平。** 避免不必要的 `client.rs` 与 `client/` 并存、层层嵌套，以及为了分类产生大量小目录。
- 按职责拆分模块，留意生命周期、调度、存储、协议和控制面的耦合。抽象应解决当前明确的问题，不为假设的扩展搭建通用框架。
- 新增 crate、公共 trait、配置项或依赖前，先判断现有模块和协议能否复用。
- **必要的地方补注释。** 优先解释并发语义、状态转换、校验/持久化边界、取消和资源释放顺序，以及难以直观看懂的原因；避免逐行翻译代码。
- SDK（`q2q-core`）的复杂测试集中在 `crates/q2q-core/tests/`，保持扁平；私有单元测试可用 `#[cfg(test)]` 和 `#[path]` 加载，公开 API 集成测试按 Cargo 配置注册。
- 解耦或结构调整应保留已有行为及约定的公共 API；确需改变兼容性时明确列出影响。

## 文档与任务记录

- `docs/` 写给使用者和开发者的能力、协议与架构说明；有中英文对应页面时同步更新。
- `todos/` 保存方案、决策、阶段进度、待办和验证记录；同一主题优先更新已有文件。
- 不重复堆放文档：部署或使用说明已有正式文档时，todo 用链接引用，不再维护第二套说明。
- 架构和调度适合用 Mermaid 图解释，图应对应真实调用、数据和生命周期关系。
- 历史验证数字属于当时的记录，不能当成本轮测试结果。未完成的 todo 不提前勾选。

## 验证与交付

- 涉及实现时，把任务要求的回归验证纳入计划；用户要求补测试时，把它作为交付的一部分完成。
- 测试关注公开行为及重要边界：并发隔离、取消、错误传播、恢复、资源清理和内容校验，不只覆盖正常路径。
- 需要联机验证时，可优先使用临时本地 Track/Punch、内存状态或本地 Redis，不必等用户部署外部测试环境。
- 本地服务测试注意 Track/Punch 的限流和残留状态，必要时每个场景使用新实例；结束后清理自己创建的服务和临时资源。
- 不将密码、私钥、生产地址或临时环境的绝对路径写入仓库约定。测试通过环境变量获取连接信息。
- 交付时简要说明改动、实际验证结果和重要限制；未运行的项目不能声称通过。

## Git 与 PR

- 新分支命名为 **`runtime/描述`**，前缀使用执行任务的 AI runtime 名称，例如 Codex 用 `codex/`、Claude 用 `claude/`、WorkBuddy 用 `workbuddy/`；描述使用简短、清楚的英文短语。
- 尊重工作目录的已有改动，不覆盖、不清理用户的工作。用户要求在原工作目录开发，不使用 Git worktree；如需切换分支，先保留已有修改。
- 用户要求 rebase 时先 fetch remote main，处理实际冲突；不要对带有未处理改动的目录盲目重置。
- 用户说“发 PR”时完成提交、推送并创建 PR，给出链接。检查 CI，发现失败就定位修复；没有证据不能说 CI 通过。
- 用户说“合了”时，以远端实际状态确认合并，并在继续开发前同步相应基线。已有用户改动需要保留。
- 创建 PR 不等于授权合并；只在用户明确要求时执行合并、发布等后续动作。

## 如何维护这些约定

新增条目前确认它来自用户的明确要求或已确认的项目决策。不要把 AI 自己的一次性实现选择、临时环境、推测或尚未批准的建议升级为长期约定。新要求与这里冲突时，以当前要求为准，并同步调整文档。

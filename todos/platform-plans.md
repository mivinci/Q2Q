# 平台套餐、购买与访问控制

状态：套餐/订阅基础已接入；真实购买、可信用量计量和额度封顶未实现。价格和用量额度不在本阶段承诺。

已落地：D1 项目订阅记录、服务端套餐目录与 entitlement 解析、存储/网络写入口的服务端能力检查、`/usage` 套餐与用量页面、项目 owner 才能操作的本地模拟切换。模拟功能仅在显式设置 `BILLING_SIMULATION=enabled` 时可用，不会扣款或改变额度；额度仍显示为待定。

## 套餐草案

| 套餐 | 面向用户 | 能力方向 |
| --- | --- | --- |
| Free | 初次体验和小规模验证 | 使用平台核心流程，提供有限的平台存储、保留期和网络服务额度 |
| Creator | 个人创作者及小型项目 | 提高托管容量、保留期和平台分发资源额度，提供完整的文件/种子管理 |
| Team | 多人协作和较高服务需求 | 更高资源上限、多人项目协作、成员管理及后续的服务保障能力 |

套餐按项目/工作空间订阅。一个项目的成员共享项目套餐；项目角色决定谁能管理成员和订阅，套餐 entitlement 决定项目可以使用哪些平台资源。两者分别校验。

单文件上限先作为第一项实际套餐限制：Free 为 2 MiB，Creator 与 Team 为 8 GiB（平台当前的绝对单文件上限）。Free 上限为 Cloudflare Workers Free 的 10 ms CPU 预算留出余量；2 MiB 数值仍需线上处理实测校准。Creator/Team 的 8 GiB 只有在处理 Worker 能获得足够 CPU 配额后才可兑现；当前 Free 处理 Worker 不支持此大小，需启用付费 CPU 配额或把哈希任务拆成可续跑的分段任务。其他存储容量、保留期限、平台出口/TURN 用量、并发额度及各档细节仍待试点和成本测量后确定。暂不按 Peer 数量收费。自带 S3 和自定义 Track 是用户接入自己的资源，不自动授予平台托管存储、出口或中继额度；平台收费能力只限制 Q2Q 实际提供的资源。

## 授权与边界

- 服务端是订阅状态、套餐 entitlement 和用量的权威来源；前端传入的 plan、额度或按钮状态不能作为授权依据。
- 每个受套餐控制的服务端入口都先验证用户对项目的角色，再验证项目订阅及对应 entitlement/额度，最后执行写入或签发凭据。
- 项目 owner 可购买、升级、降级和管理付款方式；member 可查看当前套餐和用量。界面隐藏或禁用操作只改善体验，API 仍必须独立拒绝未授权请求。
- 取消订阅默认在当前结算周期结束时生效。付款失败、降级或超额应有明确状态和宽限规则，不因账单状态变化立即删除内容或撤销已有下载授权；具体宽限时间需产品决策。
- 达到额度时先阻止新增的付费资源承诺（如新建托管对象、签发新的托管分发授权或增加超限资源），保留查看、下载/导出、删除、撤销等恢复和管理路径。是否暂停已有托管分发及通知节奏待服务等级和成本规则确定，不自动删除对象。
- 不默认自动超额扣费。若未来引入按量计费，须单独设计授权、预算上限、预估提示和对账流程。

## 用量定义

计量需要能解释平台实际承担的成本，至少分开观察：

- 平台托管对象存储容量与保留时间；
- 平台对象存储的读取/出口量；
- TURN 中继流量；
- 并发或其他可兑现的服务能力。

Peer 直连流量不代表平台的出口成本，不直接计入平台流量额度。SDK 上报可用于用户展示和诊断，不作为唯一计费证据。原生 Track/Punch/TURN 与存储侧需要提供可归属到项目、可去重、可汇总的服务端计量；高频原始事件不直接写入 D1，按批次汇总并保留对账依据。可信计量未接通前，不启用按量结算或硬性流量封顶。

## 实施方案

### 阶段 1：套餐和 entitlement 基础（已接入基础版本）

- 定义版本化的套餐目录与 entitlement key，例如 `hosted_storage`、`retention_days`、`platform_egress`、`turn_relay`、`concurrent_transfers`、`team_members`。代码中的套餐目录暂用配置表达，不把额度散落在页面条件里。
- 在 D1 为项目订阅保存 `project_id`、`plan_id`、状态、当前周期、取消时间及更新时间；补充必要的变更历史或事件记录，明确同一项目同一时刻的生效订阅规则。
- 提供服务端 `getProjectEntitlements(projectId)` 一类统一解析入口：综合套餐目录、订阅状态和当前周期，返回功能能力与限制。订阅异常/未知状态按拒绝新付费能力的安全默认处理，同时允许恢复账户的管理操作。
- 先接到项目 API 的授权边界。重点检查平台存储开通、上传授权签发、远端处理任务、发布/分享授权、项目分发网络配置等会消耗平台资源的入口。
- 项目成员邀请、编辑等继续由角色授权控制；套餐成员上限作为额外 entitlement 检查。所有检查放在服务端业务入口，不能只在页面做 `if`。

`higherLimits` 的具体数量和收费边界仍待确定。`teamCollaboration` 已通过服务端 entitlement 接入团队项目邀请创建与接受；成员数量上限、真实购买和降级后的成员访问策略仍未确定。新增付费入口时必须继续在服务端接入具体 entitlement 检查。

### 阶段 2：套餐和用量界面（已接入基础版本）

- `/usage` 按当前项目展示套餐、订阅状态、记录文件数与文件记录大小，并展示 Free 2 MiB、Creator/Team 8 GiB 的单文件上限。
- 统计值只用于界面观察，明确提示不是账单或配额依据；额度为空表示尚未定义，不等于无限。
- 只有项目 owner 能管理订阅。付款未接入时购买按钮保持不可用；本地模拟开关需显式启用。
- 后续将项目角色、订阅状态、用量状态的不同界面交互补齐，并根据现有 i18n 字典维护文案。

### 阶段 3：用量与超额策略

- 先实现可观测的聚合用量，不先收费。区分当前用量、周期用量、来源和采样时间，并在界面说明统计口径。
- 为可竞争的资源分配设计原子预留/提交/释放或等价的并发安全机制，避免两个同时发生的上传都通过额度检查后超额占用。
- 队列重试和重复服务事件使用稳定事件 ID 去重；保存可对账汇总，不把前端进度作为最终账本。
- 完成告警、接近额度提示、超限后的新增操作拒绝和恢复流程，再依据试点确定确切阈值、宽限期及既有服务的处理方式。

### 阶段 4：购买和订阅生命周期

- 先选定支付服务、币种、税务/退款要求及结算周期，再确定 checkout 与 webhook 集成；支付渠道当前未定，不在方案中假定供应商。
- 将支付实现封装为 provider 边界；支付密钥只放服务端密钥管理，浏览器不接触私钥或支付凭据。卡号等敏感支付数据由支付服务处理。
- 增加服务端创建结账会话、返回安全跳转地址、签名校验 webhook、事件幂等处理及订阅状态回写。不能只依赖浏览器 checkout 回跳确认付款成功。
- 定义试用、有效、取消待生效、已过期、付款失败/宽限等状态转换，以及升级/降级即时生效还是周期末生效。状态转换更新后由统一 entitlement 服务读取。
- 沙箱验证重复 webhook、乱序事件、取消/续费、付款失败和项目权限撤销等场景后，再配置生产价格和上线购买入口。

## 上线前需要定下来的事项

- 三档套餐的最终名称、可见功能、免费层边界、价格、币种和结算周期；
- 每项容量/流量/并发的计量口径、告警阈值、软/硬限制和超额后的现有服务策略；
- 支付服务、退款/税务处理、取消和欠费宽限规则；
- Track、Punch、TURN 与对象存储如何提供可靠、可去重的项目级计量。

这些决策完成前，可以先实现订阅模型、服务端 entitlement、模拟订阅状态、权限拦截和只读的套餐界面；实际扣款与基于用量的硬限制应在支付和计量链路可验证后启用。

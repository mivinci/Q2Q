# 产品方向

## 当前共识：开放平台与官方客户端共同推进

Q2Q 优先建设内容分发开放平台，作为官方客户端和第三方应用共同使用的基础设施。平台提供文件上传、存储接入和做种管理界面；官方客户端既是下载和做种工具，也是连接开放平台的客户端。普通用户通过界面使用，开发者通过 SDK/API 接入，两条方向可以同时成立。

这一共识取代早期“先完成独立终端产品，再将能力开放为平台”的推进顺序。下方保留早期讨论原文作为历史参考；其中旧的单 Peer 上传限制等描述属于当时状态，不能作为当前能力说明。

**本文记录产品方向与待设计范围，不表示账号、托管平台、计费、存储接入或桌面界面已经实现。** 当前已具备 Rust SDK、官方 CLI，以及文件发布、下载、恢复、下载中共享、上传资源控制和连接进度观测等基础能力；具体实现以代码及正式文档为准。

## 产品组成与职责

| 部分 | 职责 |
| --- | --- |
| 开放平台 | 项目与内容管理、上传界面、存储接入、来源及做种管理、访问权限、分发策略和用量 |
| 官方客户端 | 上传、通过种子下载、恢复、做种、管理本机带宽与存储资源，并连接平台账号与项目 |
| SDK / API | 为第三方应用提供与官方客户端一致的分发能力，避免维护两套传输实现 |
| 官方网络 | 运行 Track、Punch、必要的中继及平台存储，逐步提供运维和服务保障 |

官方客户端是平台的第一个完整应用，也用于验证 SDK 和平台接口是否足够好用。现有 CLI 是当前入口；桌面界面、浏览器接收端及其他语言 SDK 后续按具体使用场景推进。开源框架继续保留自部署价值。

## 内容、来源与分享

平台需要区分三个对象：

- **内容**：由种子和内容哈希确定，已发布版本不可变；字节改变时生成新内容版本。
- **来源**：本机、其他做种客户端、自带 Bucket 或平台存储。同一内容可以增加或更换来源，但新来源必须提供同一份可校验字节。
- **分享**：面向谁开放、何时过期、使用哪个链接或访问凭据。分享授权独立于内容身份。

基本交付路径：

```text
上传文件或接入已有对象
        ↓
生成种子，登记内容和存储来源
        ↓
分发种子或分享链接
        ↓
客户端通过 Peer 或对象存储下载并校验
        ↓
接收方按自己的设置继续做种，平台展示交付结果与来源流量
```

种子文件是现有下载入口；分享链接可以作为后续交互入口，不表示浏览器接收或磁力链元数据获取已经实现。已有对象如何生成种子和证明、对象版本如何固定、存储地址如何刷新，仍需在实现时明确。存储迁移不应改变内容身份，也不能因来源受平台管理而跳过内容校验。

## 两种存储模式

用户可以填写自己的 S3 Bucket 及相应访问配置，也可以订阅套餐使用平台提供的存储：

| 模式 | 产品含义 |
| --- | --- |
| 自带存储 | 用户连接自己的 Bucket，由自己的云账号承担该存储及相关流量费用；Q2Q 管理内容与分发接入 |
| 平台存储 | 用户购买容量与保留期限，由平台管理内容副本及相应资源 |

两种模式复用内容管理及分发接口。第一版建议先接通一种 S3 兼容存储，再根据实际需求扩展供应商；具体适配方式和首个供应商待实施方案确定。

存储连接与下载授权需要分别设计：长期访问密钥按项目限制权限、独立安全管理，不进入种子或下载客户端；客户端使用受限的访问授权。项目密钥、自签 Peer 身份、内容校验和分享访问权限各有职责，不能相互替代。账号、项目隔离、索引可见性及内容访问授权需要进入平台最小闭环。

**Peer 做种提高可用性，但离线交付保证必须依赖仍可访问的完整存储副本。** 部分块缓存、曾经在线的做种设备不能直接当作可靠保存。平台界面需明确显示当前来源及内容保留状态。

## 套餐方向：网络规模与存储规模

套餐以网络能力和存储容量为两个主要维度，具体计费单位、配额及价格需结合试点和成本测量确定，尚未定价。

| 维度 | 后续可定义的资源 |
| --- | --- |
| 存储规模 | 容量、内容保留期限 |
| 网络规模 | 分发并发额度、中继或平台出口流量、可选带宽保障 |
| 后续服务等级 | 团队管理、运行观测、服务保障和支持 |

网络规模要对应可计量的资源和可兑现的服务，暂不直接按网络中的 Peer 数量收费；节点数量不能单独说明交付能力或平台成本。自带存储不表示网络及平台服务免费，平台存储也不隐含无限流量。

应分别观测 Peer 直传、TURN 中继、对象存储/源站下载，以及平台实际承担的存储和出口成本。现有 SDK 的 payload/编码字节计数可用于传输观测，但还不是可信的服务端计费账本，不能直接用于结算，也不预先承诺固定的带宽节省比例。

## 第一阶段建议：跑通完整交付闭环

下面是实施建议，尚未拆成已批准的开发任务：

1. 用户注册并创建项目，设置项目授权和隔离边界。
2. 连接存储，上传一份文件或登记已有对象，生成可校验的种子。
3. 平台展示内容、存储来源和当前在线来源，提供上传与做种管理入口。
4. 官方客户端连接平台，通过种子下载，允许用户自行选择是否继续做种及贡献多少资源。
5. 平台展示交付是否成功、耗时及来源流量，为套餐配额和后续计费积累依据。

先让平台、官方客户端与 SDK 完成同一个使用流程，再扩展供应商、团队功能、浏览器接收、视频及直播。具体页面、服务划分、API、数据模型和部署拓扑仍需另行设计，本文不提前固定新的 crate 或技术栈。

# 早期讨论原文（历史参考）

以下保留最初的大文件交付产品与开发者托管平台讨论，历史建议与当前共识不一致时，以本文上半部分为准。

我倾向于把 Q2Q 做成一个**“从自己设备直接交付内容”的产品**：用户选中文件，生成链接，对方打开就能接收；视频进一步支持边传边看。

现在的底层能力已经能支撑这个方向，但接下来需要围绕一个具体使用场景来取舍功能。

## 我最看好的切入点：大文件交付

先服务这样一类人：

**经常给别人交付大文件的独立创作者和小团队。**

例如摄影师交付素材、设计师发送工程文件、开发者分享安装包或模型文件。这是一个值得验证的用户假设，还不能当作已经确认的需求。

用户看到的流程应该很简单：

```text
拖入文件 → 创建分享 → 发出链接 → 对方打开接收
                            ↓
                     查看进度和交付结果
```

产品需要回答的是：

- 对方有没有收到、还差多少？
- 中断后能不能接着传？
- 我的电脑关了，对方还能不能下载？
- 多个人下载时，会不会把我的网络占满？

这些问题会自然地把 SDK、官方服务和客户端串起来。

## 产品可以由三部分组成

| 部分 | 用户获得什么 |
|---|---|
| **桌面客户端** | 选择文件、创建分享、管理上传带宽、查看交付状态 |
| **浏览器接收页** | 打开链接即可接收，展示文件、来源状态和恢复进度 |
| **官方托管服务** | 自动连接、必要时中继、可选云端保留、账号与设备管理 |

开源框架继续作为基础。官方产品的价值来自安装即用、可靠交付、跨设备体验和运维保障。

这里必须明确一个产品承诺：**发布者离线时，内容由谁继续提供？**

我建议提供两种明确模式：

- **直接分享**：主要由自己的设备提供，界面清楚显示在线状态。
- **云端保留**：将副本保留到指定时间，发布者离线后仍可交付。

云端保留可以成为付费能力。中继和存储产生的实际成本，也需要纳入产品计量，不能把所有连接都视为免费直连。

## 视频很适合成为第二个亮点

文件交付跑通后，再做：

> **把本机视频发成一个可以直接打开观看的链接。**

这能发挥我们已经实现的 seek、预取和紧急块 CDN 回退。

但“能按需读取视频字节”和“完整视频产品”之间还有播放器、格式兼容、封装、转码等工作。Cloudflare Stream 的产品范围就涵盖上传、存储、编码和播放，这说明视频产品的交付链条会明显扩大。[官方介绍](https://developers.cloudflare.com/stream/)

所以我会先支持有限的视频格式，把分享与观看体验做好，再决定是否承担转码和直播。

同样，按需读取大文件本身也可以成为后续专业能力；Resilio 已将这种能力用于远程文件访问。Q2Q 是否值得进入这个市场，需要找到更具体的用户需求。[Resilio File Streaming](https://www.resilio.com/active-everywhere/features/file-streaming/)

## 第一个版本，我会控制在这个范围

1. 一个桌面端，负责发布和管理分享。
2. 一个浏览器接收页，接收方无需安装。
3. 官方运行 Track、Punch 和中继。
4. 支持断点恢复、取消、限速和交付状态。
5. 分享的访问控制与到期机制。
6. 少量真实用户，观察他们能否独立完成交付。

其中**浏览器接收端是需要尽早验证的技术关口**：现有 Rust SDK 的文件存储和 QUIC 信令不能直接搬进网页。当前发布端一次服务一个 Peer 的限制，也需要在多人交付前解决。

另外，当前已有的身份确认和内容校验，还不足以直接承诺“私密分享”。分享授权、索引可见性，以及需要时的内容加密，都应进入产品设计。

## 长期可以长成什么

我觉得可以走这条路径：

**大文件交付工具 → 文件与视频分享产品 → 面向其他应用的内容交付平台。**

自己的客户端会让我们先知道用户到底需要什么，再把成熟能力开放成托管 SDK/API。收费也更容易围绕可靠交付、云端保留、团队管理和服务保障展开。

**我最想先确认的是：你更希望 Q2Q 首先成为一个普通人直接使用的分享产品，还是一个让开发者接入的托管平台？** 我个人更倾向于先把前者做出一个明确、好用的场景。

## 开发者托管平台，具体是什么产品？

可以叫 **Q2Q Cloud**：

> **让其他应用通过 SDK 接入文件分发、设备直传和按需读取能力，由 Q2Q 负责连接、调度、回退和运行保障。**

客户是开发应用的团队，最终用户在他们自己的产品里下载或观看内容。

比如，一个模型工具需要把几十 GB 的模型交付给用户：

```text
开发者创建项目
    ↓
登记模型版本、内容校验信息和 HTTP 源站
    ↓
在自己的应用中接入 Q2Q SDK
    ↓
用户点击“下载模型”
    ↓
SDK 发现可用来源，选择 P2P 或 HTTP，恢复并校验内容
    ↓
开发者在控制台查看成功率、耗时、来源流量和费用
```

这些是拟议中的产品能力；我们现在已有底层传输能力，项目管理、托管控制台和商业服务还需要建设。

## 客户到底买到了什么？

我会把产品分成四部分：

| 部分 | 开发者得到什么 |
|---|---|
| **SDK** | 下载、恢复、取消、进度、按需读取，以及后续的多端支持 |
| **官方网络** | 托管 Track、Punch、中继，承担部署、扩容和故障处理 |
| **管理控制台** | 项目、内容版本、访问权限、用量和费用管理 |
| **运行观测** | 下载成功率、连接失败原因、完成耗时、P2P/中继/源站流量 |

客户购买的是一个可以持续运行、能够解释故障和核算效果的交付服务。

这种开源基础加官方云服务的产品关系，可以参考 LiveKit：它提供自部署能力，也通过 Cloud 提供托管网络、运行保障和观测。[LiveKit Cloud 官方说明](https://docs.livekit.io/intro/cloud/)

## 我更看好哪一种托管平台？

### 第一种：大文件分发平台——最适合先验证

目标客户可以是：

- AI 模型或数据集工具。
- 游戏启动器和资源更新工具。
- 工程软件的插件、素材与安装包分发。
- 企业内部的大文件交付应用。

共同特征是：**文件大、内容有版本、完整性要求明确，而且客户可以在接收端集成 SDK。**

这和现有 Rust SDK 很接近，也可以先从原生应用开始，逐步增加其他语言和平台支持。

不过，P2P 能否显著改善这些场景，需要实测。用户是否同时在线、是否愿意贡献上传、源站是否已经足够快，都会影响结果。当前的单 Peer 上传限制、下载后持续做种和上传资源控制，也要继续完善。

### 第二种：视频分发加速平台——适合后续扩展

客户保留自己的播放器、视频源站和业务系统，Q2Q 提供分段获取、邻近 Peer 分发和 CDN 回退。

这个方向需要浏览器 SDK、播放器接入，以及对媒体分段和播放质量的观测。

如果进一步承担上传、存储、转码、播放，就会扩展为完整视频平台。Cloudflare Stream 展示了这类产品的范围。[官方说明](https://developers.cloudflare.com/stream/)

**我会优先验证大文件分发，再决定视频业务要做到多深。**

## 第一版平台应该是什么样？

我会用一个完整的接入闭环来定义：

1. 开发者注册，创建一个项目。
2. 登记一份文件及备用 HTTP 来源，生成可信的内容描述。
3. 业务后端给用户签发短期访问凭据。
4. 应用通过 SDK 发起下载，自动处理连接、恢复与回退。
5. 控制台展示这次交付是否成功、耗时和流量来源。

项目密钥留在开发者后端，客户端只拿受限凭据。项目之间还需要隔离索引、权限和用量；现有的自签 Peer 身份不能直接替代这一层业务授权。

## 怎么形成商业价值？

可以围绕这些能力设计收费：

- 项目订阅和运行观测。
- 实际消耗的中继流量。
- 可选缓存、存储和离线交付。
- 团队管理、服务保障和技术支持。

具体计费单位需要结合试点客户和成本测量确定。尤其要区分直连流量、TURN 中继和源站/CDN 流量，不能预先承诺固定的节省比例。

**我的看法是：这个方向有机会做成“应用内的大文件交付基础设施”。** 它适合先找一两个能控制接收端的开发团队，用真实业务验证下载质量和接入成本，再逐步扩大平台能力。

# Platform API 凭据与 CLI 登录方案

状态：设计草案，尚未实现。目标是让 CLI、CI 和第三方程序安全调用平台 API，保持现有独立 Q2Q CLI/SDK 与自定义 Track 可用。平台网络准入与私有内容授权单独设计，本阶段不宣称已具备私密分享。

## 当前基础

- Platform 使用 Better Auth、GitHub OAuth 和 D1 会话；请求 hook 校验持久会话、账号状态、会话版本和到期时间。项目权限通过 `project_member` 与 owner/member 检查；套餐按项目读取。
- CLI 现有 `seed`、`magnet`、`publish`、`download` 命令使用本地 Peer 身份，不含平台登录或项目绑定。
- 当前 Track 验证 Peer 身份及会话，不识别平台用户/项目。平台下载授权是独立 bearer 凭据，和登录或 API Key 不是同一种权限。

## 目标和入口

| 场景 | 入口 | 授权来源 |
| --- | --- | --- |
| 交互式 CLI | `q2q login` | 浏览器已登录用户确认设备授权，CLI 获得设备凭据 |
| CI、脚本或第三方 | 平台创建 API Key，通过标准输入或运行环境变量提供 | 用户创建并限定权限的 API Key |
| 现有独立下载/自托管 | 原有命令及 `--track` | 保持现有 Peer 协议，不要求平台账号 |

设备凭据与 API Key 使用共同的 bearer 验证、项目与权限检查，但在记录中保留类型和生命周期；两者都不作为 Track 凭据。浏览器 Session 与 API bearer 接口分开，禁止把请求参数、项目 Cookie 或不受信任的用户头当作身份。

## 凭据模型

- D1 保存凭据 ID、公开识别前缀、类型（设备或 API Key）、所属用户、名称、允许的权限、允许的项目范围、创建/到期/撤销时间、最近使用时间和密钥校验值。随机秘密至少 256 bit，服务端只存 SHA-256 校验值；凭据仅创建时返回一次，不存明文。
- API Key 默认限定一个或明确选择的多个项目；不默认包含将来加入的新项目。项目列表或授予资格仅限当前成员项目。请求时取凭据范围、当前成员角色、账号状态和业务授权的交集；删除成员、角色变化或禁用账号后，下一次请求立即失去相应权限。
- 初始 scope 最小化：`projects:read`、`files:read`、`files:write`、`publications:read`、`publications:write`；暂不开放成员、套餐、支付、存储密钥和管理员操作。写权限不自动扩大用户角色或套餐能力。将来需要申请 Track 凭据时再新增独立 scope。
- 凭据有明确到期时间、单独撤销与轮换；创建、撤销和敏感授权变更记录审计（不记录 secret）。最近使用时间限频异步或条件更新，不能因观测写入导致有效请求失败。
- 设备凭据首版不设计长期自动刷新；到期后重新登录。API Key 用于非交互式长周期任务，必须设有效期，具体默认值与最长值在实现前确定。服务端返回可解释的已过期/已撤销错误，不泄露其他用户凭据是否存在。
- 现有 Admin「禁用账号」必须同时阻止所有凭据使用；「撤销全部平台会话」当前只撤销浏览器会话，首版保持该边界并在用户界面明确说明设备/API 凭据需单独撤销。若要一键撤销全部凭据，先单独确认并设计，不复用会影响现有会话的 `authVersion` 隐式改变语义。

## CLI 设备授权

首选标准设备授权模式；先核对当前 Better Auth 版本及其设备授权插件在 Workers/D1 的支持，再决定复用插件还是实现最小协议。不可在尚未核实插件能力前假定可用。

1. CLI 对配置的 Platform origin 发起设备授权请求，取得高熵 device code、短期 user code、验证地址、到期时间和轮询间隔。device code 只由 CLI 保存，用户输入短码到平台；浏览器地址不携带设备秘密。
2. 浏览器用现有平台登录，展示设备名称、申请的项目和权限；用户明确确认后服务端将授权绑定到已认证用户。拒绝和过期均终止授权；项目权限在确认及凭据签发时重新校验。
3. CLI 在限速和期限内轮询；仅可一次性换取设备凭据。设备 code 和 user code 存校验值，使用原子状态变更防止双重兑换和竞争。返回 pending、slow_down、denied、expired 等明确状态，不允许无限轮询或短码暴力猜测。
4. 授权界面展示用户输入的短码及设备信息，防止错误设备被授权；防钓鱼提示不能替代核对。若换取结果丢失，不重放明文凭据；重新发起授权。CLI 可显示 URL 和短码，浏览器不可用时仍可在另一设备完成。
5. CLI 凭据优先使用系统凭据库；不可用时采用受限权限的本地凭据文件，并明确提示。配置目录使用现有 Q2Q 状态根目录，但秘密独立存放；权限、原子写入、并发和不同系统 ACL 需逐平台验证。提供 `q2q logout` 清理本地凭据并尽力撤销服务端设备凭据，离线撤销结果需明确提示。

## API Key 与 API 边界

- 平台账号设置提供创建、列表、查看权限、撤销；创建时明确显示项目、scope 和到期时间，明文只显示一次。创建/撤销使用现有 Cookie Session、同源/CSRF 与账号检查，不可用 API Key 创建或扩大自身权限。
- 首版 API 按 `/api/v1/` 定义明确公开契约，`Authorization: Bearer ...`；仅 bearer、仅 TLS，严禁 query string、日志或重定向透传凭据。API 不接受浏览器 Session 作为隐式替代，业务服务层复用现有项目与 entitlement 校验。
- CLI 使用 `Q2Q_API_KEY` 进行非交互式临时覆盖，不将该值写入配置；命令行参数不接收秘密，避免 shell 历史与进程列表泄露。禁止输出秘密、完整授权头、外部签名 URL 或设备 code。
- 错误约定：认证缺失/失效 401，已认证但权限不足 403，未授权项目按现有语义 404；超限 429，服务故障 503。并发写入需要在数据库写入处复核成员和账号状态，不能仅在入口校验。
- 第一批 API 先支持当前用户、允许的项目列表和项目选择；发布/上传 API 在单独阶段适配现有上传、配额、失败恢复和幂等机制。现有浏览器使用的 `/api/` 不能直接全量暴露给 API Key。
- API Key 和设备凭据的本地存储、平台 origin、超时和错误处理不得受全局 `--insecure` 静默放宽；生产只允许 HTTPS，开发环境的本地 HTTP 明确限制 loopback。

## Track 与自定义服务

平台凭据仅发送到用户明确选择的 Platform origin，不附加到种子、磁力链、Peer、下载来源或任意 Track。官方 Track 未来需要项目准入时，CLI 向平台申请带 audience、Peer 身份、权限和短期过期的专用授权；Track 验签并复核能力的具体策略另行设计。自定义 Track 可采用开放模式或自己认可的授权协议；是否信任平台签发者由部署者配置。

Track 准入不等于内容保密：私有 Peer 发现、Peer 数据面授权、平台存储下载授权、分享撤回和已下载文件边界要作为单独需求设计。按项目计量也不应仅凭客户端自报建立可信账本。

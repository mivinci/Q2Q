# 下载中共享的读写解耦

## 状态

待实施。先记录方案；当前优先评估产品与接入方向，不立即启动此项优化。

## 动机

上传热点缓存已完成，见 [upload-block-cache.md](upload-block-cache.md)。下载目标的上传读取、证明读取和下载提交仍经过 Destination 的同一把存储锁。缓存未命中时可能延迟新块提交；实际影响需要测量，不能预先承诺收益。

## 实施顺序

- [ ] 建立边下载边上传的对照工作负载，分别记录锁等待、块提交延迟、读取校验次数和总耗时，覆盖热点与不同块。
- [ ] 核对数据文件、证明记录与恢复压缩的生命周期：明确已提交记录的偏移、长度和文件句柄如何形成稳定读取信息。
- [ ] 锁内仅获取已提交块的必要状态与读取信息；使用原文件句柄按偏移读取，在锁外验证字节和 Merkle 证明，不依赖共享游标。
- [ ] 下载写入、恢复记录追加及持久化仍串行执行，保留失败后禁止继续提交的语义；评估缓存 revision 检查是否仍有长临界区。
- [ ] 补充上传/提交并行、未提交块拒绝读取、源与证明篡改、取消、关闭、恢复及阻塞任务资源释放回归。
- [ ] 使用相同负载比较优化前后结果，执行工作区与本地 Track/Punch 回归，并同步双语数据面文档。

## 正确性边界

- 可上传以数据及证明恢复记录提交成功为界，不能因位图提前更新而暴露未提交字节。
- 不能只把 Mutex 换为 RwLock：先处理文件游标和证明记录访问，再缩小锁范围。
- 读取中的文件句柄与记录必须在任务结束前有效；取消不能提前释放读取额度、连接额度或目标文件所有权。
- 锁外读取仍验证到 Seed 的根，来源错误与共享关闭保持既有传播方式，防止关闭后缓存回填。
- 复用现有上传读取额度和有界缓存，保持公开 API 不变，不新增 crate；目录保持扁平，必要处解释并发及持久化顺序。

## 决策依据

测量后再决定拆分范围。如果锁等待不是主要开销，记录结果并降低优先级，不为了结构调整增加持久化复杂度。
